# 会话流与右侧文件改动视图：设计讨论

资料核对于 2026-10-01 至 10-02；这是讨论稿，不是已实施规格。

## 已核实的 Claude Code 当前行为

官方文档与 CHANGELOG 一致：终端版自 v2.1.260 增加 fullscreen 下的持久 diff 侧栏。

- `/diff` 在会话旁打开面板，包含变更文件列表、每文件增删数和 diff；编辑或执行 shell 命令后刷新。
- 条件：fullscreen、Git 仓库、至少 110 列；至少 144 列时首次编辑自动打开。
- 手动打开和关闭的选择会影响后续会话自动出现行为。
- 可点击文件、独立滚动、选中代码行并附到下一条提问；可切换本会话、未提交、分支比较基线。
- 非 fullscreen 的经典终端渲染使用占据输入区的 diff viewer，看完再返回。
- Fullscreen 使用终端 alternate screen buffer，仅渲染可见消息，输入框固定；复制、搜索、滚动由应用处理，另有导出到终端原生 scrollback 的入口。官方目前标为 research preview。
- 终端 `/focus` 进一步压缩工具活动；桌面版 Normal 保留工具摘要、Thinking 展开思考、Verbose 展开过程；VS Code 扩展另有 Focus view。不同产品入口不能混同。

## 建议的信息分工

| 区域 | 核心内容 | 更新规律 |
|---|---|---|
| 左侧会话流 | 用户要求、Agent 解释、进展、结果、错误、精简工具摘要 | 按发生顺序保留 |
| 左下输入与必要交互 | 草稿、补全、提问、审批 | 始终容易找到，不被文件刷新打断 |
| 右侧文件改动 | 文件清单、选中文件、代码上下文、行号和增删、比较范围 | 反映当前审阅状态，不重复追加进聊天 |
| 底部状态 | 模型、权限、上下文用量等 | 全局信息，可考虑贯穿两栏 |

左侧仍保留“修改 src/a.js，+12 −4”这样的证据与入口；完整 diff 在右侧或窄屏全文视图读取。失败与需用户回答的内容必须在会话侧可见。关闭右侧时应仍能通过摘要打开完整改动。

## 布局和交互建议

- 右侧先占约 40%—45%，使用 unified diff；在已经分成会话/文件两栏后，再把文件分成旧/新两栏通常过窄。
- 用左右最小可读宽度决定是否分栏，不只判断百分比。现有 96 列、36% 意味右侧仅约 34 列，代码阅读空间有限。可把 120 列手动分栏、144 列自动出现作为初步验证值，不当作最终结论。
- 无改动时会话可占满；开始编辑时出现，此后保持布局稳定，回合结束保留改动。用户手动关闭后不因下一次工具调用立即重开。
- 默认键盘焦点在输入；显式切换到文件区后支持选择文件、上下翻页、横向查看长行或展开全文；保留 Tab 的输入补全用途。
- 自动跟随最近编辑，但用户选文件或滚动后暂停跟随；显示“有新改动／继续跟随”，避免抢走阅读位置。
- 选中代码后附上文件、行号及选区快照，再回到输入提问。后台文件变化时，已选内容应保持与用户当时选中内容一致。
- 首版定位为改动审阅视图。是否需要在右栏直接手工编辑文件是独立能力，后续根据实际需求决定。

## 与当前实现的差距

`src/app.js` 已有 `/pane auto|on|off`，36% 右栏、96 列阈值和 nonCapturing overlay；`src/edit-pane.js` 展示最后一次 diff 调用，自动定位最后一处变化，回合结束保留。

缺口主要是内容模型与交互：

1. `view.editPane` 只有一个 callId，新调用覆盖旧调用；需要按文件组织可审阅记录和选择状态。
2. 没有独立滚动、文件切换或选区引用；长行截断，较大 diff 只能看到自动选出的片段。
3. 只跟踪声明 diff 展示意图的工具；通过 Bash、格式化器等发生的改动不一定进入面板。
4. 需要区分“拟修改内容”“工具完成”“磁盘当前内容”；工具卡的成功不能替代文件状态核验。
5. 必须标明比较基线。Git 未提交改动可能早于当前会话或来自用户，不应全部写成“Agent 本轮改动”。工具事件适合提示进度，磁盘/Git 快照适合确认当前结果；两者配合。

## 实现路线的取舍

当前 pi-tui 路径依赖终端原生 scrollback，右栏采用 overlay。可在这条路线上先验证文件列表、键盘审阅和自动跟随规则；但要重新验证长会话、窗口缩放、复制与左右内容更新，不能仅凭 overlay 声称原生历史始终干净。

如果目标包含稳定的双区鼠标滚动、选区引用、固定输入和长会话虚拟化，Claude Code 的 fullscreen 路线更匹配：应用负责两个 viewport。代价是原生终端搜索、选择与滚动需要应用级替代或导出入口。

因此可分开做产品决定与渲染决定：先认定“会话流 + 文件改动区”的信息架构，再根据所需交互深度选择保留现有渲染或引入 fullscreen。Cordis 服务和 Agent 内核不需要因此重构。
