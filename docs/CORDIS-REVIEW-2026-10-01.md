# Cordis / DSH TUI 设计审查

审查基线：`ac880bb`，2026-10-01。范围是本地 Cordis 4.0.4、DSH 预设运行时，以及本仓库 51 个提交（2026-09-30 至 10-01）。未获取上游 Cordis 的完整提交历史；本文不能用于推论其长期质量。仅新增审查记录，未修改产品代码、用户配置或安装插件。

## 判断依据与结论

一个可组合的 Agent 应用至少要回答四个问题：能力由谁提供、对哪个会话有效、什么时候可用、失败之后用户如何继续。

Cordis 的依赖注入、作用域与生命周期主要解决前三者的底层机制，适合 DSH 的多前端、多会话、多工具组合。当前不足主要在 DSH 装配契约和 TUI 产品层：机制中的多种状态没有被转换成用户可理解、可恢复的操作。因此建议保留 Cordis，先把装配状态与使用闭环做完整。

需要区分三个层次：Cordis 是插件框架；DSH 的 profile/bundle/preset 是应用组合方式；本项目是消费这些能力的终端界面。401 不展示、回车协议不适配、弹窗闭包错误属于界面集成问题，不能归为 Cordis 核心缺陷。

## 做得好的部分

- **依赖与资源所有权明确。** 隔离实验中，声明依赖的插件在服务不存在时保持 PENDING；提供服务后变 ACTIVE 并启动一次；撤回服务后清理一次、重新进入 PENDING。此机制实测有效。
- **宿主与会话能力分层合理。** `cordis.patch.yml` 把跨会话注册表留在宿主，把面向模型的工具与提示词放入预设。避免每个会话重复创建全局服务，也支持会话之间不同能力组合。
- **有一致性意识。** 模型、权限、预设选择记录到原生会话事件；聊天记录与模型上下文区分；恢复会话采用先准备新会话、严格保存旧会话、再交接的方式。见 `src/kernel.js`、`src/session-switch.js`、`src/projection.js`。
- **界面扩展有真正的撤销机制。** `src/registry.js` 采用所有权栈支持乱序卸载，比全局变量覆盖更适合插件组合。

## 当前仍存在的问题，按优先级排列

### P1：启动依赖出错时，修复入口也不可用

`src/kernel.js:187` 在创建界面之前每 250ms 尝试解析预设，最长重试 20 秒。`src/index.js:123` 等待 createKernel 成功，之后才在 `src/index.js:613` 创建 App。因此预设缺失时无法通过 TUI 的 `/doctor` 自救。

另外，代码只声明 `inject = ['dshTuiStartup']`，但 `cordis.patch.yml:91` 声明了 agents/sessions/agentDefaultModel 等硬依赖。Loader 的 `src/index.ts:134` 将行级 inject 合并到插件依赖；它并非注释所说的“只保证顺序”。缺服务时，apply 内的友好错误检查可能根本不会执行。

建议：由宿主提供独立于业务会话的启动诊断；按能力报告“等待、失败、可用”及依赖链。界面壳先可用，再接入会话。为预设定义建立明确的就绪信号，区分等待注册与确定不存在，减少轮询。

### P1：创造模式没有完成“创建 → 使用”的闭环

`src/index.js:357` 提示“新预设装好后即可 /preset 选择”。但 DSH 的 preset registry `select()` 在 `turnBoundary.lastTurn > 0` 或回合未结束时抛出 `agent-preset/locked`。创建预设本身产生回合，原会话随后已不能切换。

现有 TUI 本地命令与工作台没有新建会话入口。它确实告诉用户可以重开会话，但没有把这一步接成操作；宿主是否额外提供等价命令不在此保证范围内。

建议：在已开展工作的会话中选择预设时，提供“保存当前会话并用该预设新建”；创造模式结束后引导“使用新预设开始会话”。无需放松内核保护已有会话工具组合的约束。

### P1：错误与取消仍然混淆，损坏能力还会被隐藏

`src/prompts.js:243` 的选择器错误处理默认直接 `finish(undefined)`；只有开启 DEBUG 才输出部分错误。`open()` 中构建或 showOverlay 失败也返回 undefined。

隔离复现：让 showOverlay 抛异常和真实发送 Esc，两种情况结果均为 undefined，没有异常传给调用方。现有测试验证了“不挂住”，但没有要求错误对用户可见。

`src/index.js:303` 又会过滤所有带 broken 的预设，`/doctor` 主要检查 `ctx.get(name)` 是否存在。服务存在、预设损坏、当前会话不能使用这些状态无法通过同一入口解释。

建议：弹窗结果区分取消与失败；失败必须有可见回执。坏掉的预设保留在列表中、禁止选择、显示原因和修复入口。诊断同时覆盖服务存在性、预设依赖、会话作用域与交互接入。

### P2：模型选择的缓存和保存范围不透明

`src/index.js:245` 首次加载模型目录后一直缓存，没有失效或刷新路径；若首次读取恰逢渠道尚未注册，空结果也会被保留。运行期间变更渠道后，选择器可能继续显示旧目录。是否在用户真实配置中触发尚未实机验证。

切模型同时写会话事件、调用 `agentDefaultModel.saveSelection()`、写 `~/.dsh-tui/config.json`。TUI 偏好默认不按 profile 或工作区分隔。用户很难知道本次切换将影响哪个下一次会话；能确认存在多重写入，不能仅凭本仓库断言内核默认设置影响所有 profile。

建议：显示有效值来源与保存范围；区分“本会话使用”和“设为默认”。目录随渠道变更失效，并保留手动刷新。

### P2：为隐藏插件日志清空整个终端历史，代价偏大

`src/app.js:614` 无条件发送 `2J + 3J + H`。支持 3J 的终端会同时清除更早的 shell 输出。该效果是历史需求驱动、已有记录的取舍，不能说是未经授权；但作为默认产品行为，范围超过隐藏两行启动日志。

建议：在宿主启动阶段统一管理日志输出与 TUI 接管顺序，让插件使用日志服务。需要清除历史时提供明确选项；保留现有偏好的选择权。

### P2：命令行值解析仍有可复现错误

实际执行 `parseArgs(['--model', '--preset', 'cordis'])` 得到 `model='--preset'`、`prompt='cordis'`，且无 error。`src/startup.js` 只校验下一个词是否为空，没有识别它是否另一个已知参数。

这会把拼写或漏值问题转换成意外启动参数，而不是用法错误。应明确区分显式 TUI 启动与作为其他宿主的附属插件，再分别处理本应用错误参数和不属于自己的参数。

### P2：能力文案与能力实际可用性不是同一来源

无 permissionPresets 服务时，`createCommandSystem().listAll()` 仍包含 `/permission`；执行后才提示缺服务。README 则说缺服务时入口隐藏。直接隔离调用已复现这个差异。

建议不再分散维护可用性判断、帮助、补全、快捷键与诊断，统一从能力状态生成。可见但禁用或完全隐藏是产品选择，两者必须与文档一致。

## 维护成本与建议顺序

TUI 主 patch 通过禁用多个 base 行、再在四份 preset 中重建能力组合实现会话隔离。设计意图合理，但与 base 行名、配置替换语义以及宿主依赖关系耦合较深。配置行按 id 覆盖时整体替换 config，用户修改一个字段可能需要重述其余字段；需要有效配置预览、来源追踪和依赖验证。

“只有 kernel.js 导入 DSH 包”是有用约束，但不是完全的运行时隔离：index/footer/commands 仍通过字符串 `ctx.get()` 使用多项原生服务。后续应逐步把这些契约归到桥接层，以减少版本升级时同时改多个文件。

建议顺序：

1. 把当前静默错误变成可见失败，展示损坏预设及具体原因；补新建会话与使用新预设路径。
2. 让启动诊断独立于会话创建，统一能力状态，理清 loader / service / preset 三种就绪状态。
3. 收敛模型默认设置、目录缓存和日志输出的所有权；提供配置来源追踪。
4. 增加少量跨边界验收：缺一个宿主依赖能否诊断；创建预设后能否开始使用；弹窗渲染失败能否继续；模型目录变化能否刷新。

无需为此重写 Cordis，也不建议继续先扩展视觉配置。应当优先降低一次普通操作需要用户理解的内部概念数量。
